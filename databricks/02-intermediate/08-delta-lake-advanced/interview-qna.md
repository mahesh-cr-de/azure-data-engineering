# Interview Q&A — Delta Lake Advanced

**Q1. How does Delta Lake's Time Travel actually work under the hood — is it storing full copies of the table per version?**
> No — Delta never stores full table copies. The transaction log records each version as a set of file-add and file-remove operations; the table's state "as of version 12" is simply the result of replaying the log up to that commit to determine which underlying Parquet files are logically part of the table at that point. Time Travel works as long as (a) the log's own metadata retention window still covers that version, and (b) the actual data files those old commits reference haven't been physically deleted — which is why VACUUM directly threatens Time Travel: it deletes exactly those unreferenced-but-old files.

**Q2. Walk me through what MERGE INTO does that you couldn't achieve with separate INSERT/UPDATE/DELETE statements.**
> Running separate statements against a target table isn't atomic as a whole — a failure partway through could leave the target in an inconsistent state, and concurrent readers could see a partial application of the changes. MERGE INTO expresses the entire upsert (and optional delete) logic as one statement evaluated against a join between source and target, and the whole thing commits as a single atomic transaction in the Delta log — either the full set of inserts/updates/deletes lands, or none of it does. It's also simpler to express correctly: SCD Type 2 and CDC-based upserts become one conditional MERGE rather than manually computing a diff and issuing multiple write paths.

**Q3. What's the difference between OPTIMIZE and OPTIMIZE ... ZORDER BY, and when would you use each?**
> Plain OPTIMIZE does bin-packing compaction — it combines many small files into fewer, well-sized ones, purely to fix the small-file problem and improve scan efficiency; it doesn't consider the *content* of the data when deciding how to group rows into files. ZORDER BY additionally clusters rows with similar values in the specified columns into the same files, using a space-filling curve, so that Delta's file-level min/max statistics can skip far more files when a query filters on those columns. I'd reach for plain OPTIMIZE whenever a table has accumulated small files (e.g., from frequent streaming writes), and add ZORDER BY specifically on high-cardinality columns that are filtered often but aren't the on-disk partition column.

**Q4. A data scientist complains that a query with `VERSION AS OF 45` used to work last month and now fails. What's the most likely cause?**
> Almost certainly VACUUM ran and physically deleted the data files that version 45 depended on, because they fell outside the retention window (default 7 days) and were no longer referenced by the current table version. This is expected behavior, not a bug — VACUUM's whole purpose is reclaiming space from files no longer needed for the *current* state, and by design it doesn't know or care that someone might still want to Time Travel to an older version beyond the retention period. The fix going forward is either extending retention for tables where Time Travel over longer windows matters, or archiving specific versions the team needs to keep (e.g., via `RESTORE` into a separate table) before they age out.

**Q5. Why does Databricks warn against running `VACUUM ... RETAIN 0 HOURS`?**
> Retention isn't just about Time Travel — it also protects any query or job that's currently reading an older snapshot of the table (Delta's snapshot isolation means a long-running read holds a consistent view of the table as of when it started, even if writes happen concurrently). If VACUUM deletes files with zero retention, a concurrent reader still working through that older snapshot can have the files it's mid-read on disappear from underneath it, causing the read to fail. The default retention (7 days) and the safety check that blocks shorter values exist specifically to guard against this, and overriding it is something you'd only do deliberately, with full awareness of every job that might be reading the table.

**Q6. How would you decide whether a table needs Z-ordering, and on which column?**
> I'd look at query patterns first — Z-ordering only pays off on columns that are frequently used in filter predicates but have too high a cardinality to be a sensible on-disk partition column (partitioning already handles coarse, low-cardinality filtering like date). A common real case is a large fact table partitioned by date, where queries also frequently filter by `customer_id` or `product_id` — Z-ordering by that column lets file-level statistics skip files within each date partition too. I'd validate the benefit by comparing files-scanned/bytes-read before and after (visible in the query's Spark UI metrics or `DESCRIBE DETAIL`), rather than applying it speculatively, since it's a non-trivial write cost to run.
