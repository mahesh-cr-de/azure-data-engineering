# Interview Q&A — Data Ingestion Basics

**Q1. What's wrong with DBFS mounts from a governance perspective, and what replaced them?**
> A DBFS mount attaches cloud storage at a workspace-level path using credentials configured once for the mount — those credentials are then effectively shared by anyone with access to that path, regardless of their individual permissions on the underlying storage. This makes fine-grained, per-user access control and auditing essentially impossible at the mount layer. Unity Catalog Volumes replaced this pattern for file-based access: a Volume is a catalog-registered object with the same permission model (GRANT/REVOKE, audit logging, lineage) as a governed table, just for non-tabular files.

**Q2. Explain what makes `COPY INTO` idempotent, and why that matters operationally.**
> `COPY INTO` tracks internally which source files it has already successfully loaded into the target table, so re-running the exact same `COPY INTO` statement against the same source location doesn't reprocess or duplicate files it already ingested — only genuinely new files get loaded. This matters operationally because it means you can schedule `COPY INTO` on a simple recurring cadence (e.g., hourly) without writing custom "which files have I already seen" bookkeeping logic, and safely re-run it after a failure without fear of duplicating data.

**Q3. When would you choose `COPY INTO` over Auto Loader, and vice versa?**
> `COPY INTO` fits periodic batch loads with a relatively bounded, moderate number of new files per run — it's pure SQL, simple to reason about, and adequate for many straightforward recurring ingestion jobs. Auto Loader (`cloudFiles`) is built for continuous or very high-volume/high-frequency file arrival, especially when paired with file notification mode (Event Grid-backed) instead of directory listing, since re-listing a massive directory tree repeatedly doesn't scale. In practice: start simple with `COPY INTO` for straightforward batch jobs, move to Auto Loader when file volume/frequency grows large enough that directory-listing-based approaches start to show real latency or cost problems.

**Q4. What's the difference between Auto Loader's directory listing mode and file notification mode?**
> Directory listing mode periodically lists the target cloud storage path to discover new files — simple to set up, but its cost and latency grow with the number of files in the directory, since it has to re-scan. File notification mode instead subscribes to cloud-native event notifications (Azure Event Grid + Queue Storage) that fire when a new blob lands, so Auto Loader is notified of new files directly instead of re-scanning — this scales much better for high file-arrival-rate scenarios (e.g., IoT-style continuous small file drops) where directory listing would become a bottleneck.

**Q5. How does Auto Loader's schema evolution actually work, and what's the operational risk if you don't configure it deliberately?**
> Auto Loader infers a schema from sample files at first run and persists that inferred schema plus its evolution history at the path given by `cloudFiles.schemaLocation`. As new files arrive with additional columns, Auto Loader can automatically evolve the target schema to include them, tracking each schema version. The operational risk of leaving this on defaults without thought: an upstream system's accidental or malformed schema change (e.g., a typo'd column name, or a field that should have been rejected) can silently propagate into your bronze table as a "new column" rather than triggering an alert — worth pairing schema evolution with monitoring/alerting on schema-change events rather than treating it as fully silent automation.

**Q6. Design the ingestion path for raw files (JSON) landing continuously from an external partner system, with governance requirements.**
> Land files into a Unity Catalog Volume (not a raw storage mount) so the landing zone itself is access-controlled and auditable from the moment files arrive. Point Auto Loader at that Volume path with `cloudFiles.format = json`, file notification mode if volume/frequency is high, and a schema location for evolution tracking, writing into a bronze Delta table with `trigger(availableNow=True)` scheduled via a Workflow if near-real-time isn't required (or a continuous trigger if it is). This gives fully governed lineage from raw file arrival through to the bronze table, with idempotent, checkpoint-tracked processing rather than custom "which files have I seen" logic.
