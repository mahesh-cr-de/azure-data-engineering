# Interview Q&A — Notebooks, Languages, Repos & Databricks CLI

**Q1. How does a single notebook support multiple languages, and what's actually happening under the hood?**
> Every notebook has a default language, but any individual cell can override it with a magic command prefix (`%python`, `%sql`, `%scala`, `%r`), plus special magics like `%sh` for shell commands on the driver and `%fs` for DBFS shorthand. Under the hood, Databricks routes each cell's execution to the appropriate language runtime/REPL attached to the cluster — variables defined in a Python cell aren't automatically visible to a SQL cell's namespace the way you might assume, though you can bridge across languages via temp views (`df.createOrReplaceTempView(...)` then query it from `%sql`) or the `spark` object each language environment shares access to.

**Q2. What's `dbutils` and name three things you'd actually use it for.**
> `dbutils` is Databricks' notebook utility API, injected automatically into every notebook/job context. Three concrete uses: (1) `dbutils.widgets` to parameterize a notebook so a job can pass in different inputs like a run date without editing the notebook itself, (2) `dbutils.secrets.get(scope, key)` to pull a credential from a Key Vault-backed secret scope without ever hardcoding it in source, (3) `dbutils.fs.ls/cp/mv/rm` for scripting filesystem operations against DBFS or mounted storage directly from a notebook cell.

**Q3. What's the difference between `%run` and importing a Python module from a Repo, and which is the better practice?**
> `%run ./other_notebook` textually splices another notebook's cells into the current notebook's execution context at that point — quick, but it tightly couples notebooks, doesn't behave like normal code (no proper namespacing, harder to unit test), and doesn't version as cleanly as a real module. Importing from a Repo treats shared logic as an actual Python package checked into source control, which you can unit test independently, reuse across many notebooks/jobs without copy-paste, and review via normal PR diffs. For anything beyond a quick prototype, the module-import approach is the better practice — `%run` is more of a notebook-era pattern that mature codebases are moving away from.

**Q4. Why should a production job reference a specific commit or branch tag in a Repo rather than just "the repo path"?**
> Because a Repos checkout is a live, editable working copy — if a job is configured to just run "the notebook at this path" and a developer is mid-edit (even just saving a work-in-progress change) on that same branch, the production job can pick up unintended, unreviewed code on its next scheduled run. Pinning to a specific commit SHA or a protected tag/branch (updated only through a deliberate deploy step, e.g. via CI/CD) guarantees the job always runs exactly the code that was reviewed and approved, decoupled from anyone's live editing.

**Q5. What's the practical difference between a Personal Access Token and a Service Principal for authentication, and which should a CI/CD pipeline use?**
> A PAT is tied to an individual user's identity and permissions — if that person changes roles, leaves the company, or their token expires/rotates, anything depending on that PAT breaks. A Service Principal (Azure AD/Entra ID identity) has its own independently-managed permissions and lifecycle, not tied to any one human. CI/CD pipelines, scheduled jobs, and any non-interactive automation should use a Service Principal specifically so the automation doesn't silently break — or worse, inherit excessive human permissions — when an individual's account status changes.

**Q6. What does the Databricks CLI actually let you automate that the UI can't (or shouldn't) handle?**
> The CLI (and the underlying REST API it wraps) enables scripted, repeatable operations: bulk workspace import/export, triggering and monitoring job runs from an external orchestrator, managing cluster lifecycle as part of a deployment pipeline, and — combined with Databricks Asset Bundles — deploying jobs/pipelines/cluster definitions as declarative YAML "infrastructure as code" via `databricks bundle deploy`. The UI is fine for one-off human interaction, but anything that needs to be repeatable, reviewable, and part of CI/CD needs the CLI/API/DABs path instead.

**Q7. A notebook works perfectly when run interactively but fails when triggered as a scheduled job. What's your first hypothesis?**
> Stale REPL state — interactive notebooks keep variables, imports, and prior cell outputs alive across re-runs on an attached cluster, so a notebook can "work" interactively because of a variable or import left over from an earlier out-of-order cell execution that isn't actually defined by the notebook's current top-to-bottom logic. A scheduled job run always starts from a clean state and executes cells strictly in order, so any hidden dependency on stale interactive state surfaces immediately as a failure. First step to confirm: use "Run All" from a freshly restarted/detached cluster and see if it still works — that reproduces the job's actual execution conditions.
