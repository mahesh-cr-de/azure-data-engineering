# Interview Q&A — Delta Lake Fundamentals

**Q1. What exactly is Delta Lake — is it a file format, a database, or something else?**
> Delta Lake is an open table format: your data is stored as standard Parquet files, plus a `_delta_log` directory containing an ordered sequence of JSON commit files (and periodic Parquet checkpoints) that record every add/remove/schema/metadata action ever applied to the table. The log is what turns a plain folder of Parquet files into a transactional table — Delta itself isn't a database engine, it's a protocol that any compatible engine (Spark, Trino, Presto, etc.) can read and write.

**Q2. How does Delta Lake achieve ACID transactions on object storage, which has no native transactions?**
> Through the transaction log combined with optimistic concurrency control. A writer stages new Parquet data files, then attempts to atomically create the *next* sequential log JSON file (e.g., `000...042.json`) using the storage layer's atomic "put if not exists" semantics (or a Databricks-managed commit service for Unity Catalog tables). If another writer already claimed that version, the losing writer detects the conflict, re-reads the latest state, and either retries or fails — this is what gives isolation and atomicity without needing storage-level locks.

**Q3. What's the difference between `DELETE` and `VACUUM` in Delta Lake?**
> `DELETE` (or an `UPDATE`/`MERGE` that removes rows) is a logical operation — Delta writes new Parquet files without the deleted rows and marks the old files as `remove` in the transaction log, but the old physical files are **not** deleted from storage. `VACUUM` is what physically deletes files that are no longer referenced by the current table version and are older than the retention threshold (default 7 days). Until VACUUM runs, you can still time-travel back to before the delete; after VACUUM, you can't go further back than the retention window.

**Q4. Explain Time Travel and its limitations.**
> Because the transaction log records every commit, you can query the table `AS OF` a specific version number or timestamp, which Delta reconstructs by replaying (or reading a checkpoint plus subsequent) log entries up to that point and reading only the Parquet files valid at that version. The limitation is retention: `delta.logRetentionDuration` controls how long log history is kept (default 30 days) and VACUUM's retention controls how long the underlying data files survive (default 7 days) — once files are vacuumed, you can't time travel to versions that depended on them, even if the log entry itself still exists.

**Q5. What's the small-file problem and how do you fix it in Delta?**
> Frequent small writes — streaming micro-batches, many small MERGE operations, over-partitioned tables — produce lots of small Parquet files, which hurts read performance because of the per-file overhead in listing, opening, and reading metadata for thousands of tiny files. The fix is `OPTIMIZE table`, which compacts small files into fewer, right-sized files (targeting ~1GB by default), typically run on a schedule after high-frequency write windows. Databricks' **Auto Optimize** / **Optimized Writes** features can also do this proactively at write time.

**Q6. What does `ZORDER BY` actually do, and when is it worth using?**
> It physically co-locates rows with similar values of the Z-order column(s) within the same files, using a space-filling curve across (potentially multiple) columns. Combined with Delta's file-level min/max statistics, this lets the query engine skip entire files during a scan when a filter on the Z-ordered column excludes that file's value range — i.e., it improves data skipping. It's worth using on high-cardinality columns that are frequently filtered on (e.g., customer_id, event_date) — not on low-cardinality or rarely-filtered columns, where the benefit is marginal and the OPTIMIZE job cost isn't worth it.

**Q7. Walk through what `MERGE INTO` compiles down to — is it really an atomic update?**
> Internally, `MERGE` reads the source and target, computes matched/not-matched row sets, and writes **new** Parquet files containing the merged result for any file touched by an insert/update/delete — it never edits an existing Parquet file in place (Parquet is immutable). The old files are marked `remove` and new files `add` in a single log commit, so from a reader's perspective the merge appears atomically — you never see a partially-applied merge.

**Q8. Managed vs. external Delta table — what's the practical difference?**
> A managed table has its data location controlled by the metastore/catalog (typically under a configured managed storage root); dropping the table deletes both metadata *and* the underlying data files. An external table is registered against a path/location you specify explicitly; dropping it removes only the catalog entry, leaving the data files intact. Production pipelines commonly prefer external/UC-governed tables with explicit storage locations for clearer ownership and to avoid accidental data loss on a `DROP TABLE`.

**Q9. Schema enforcement blocked a legitimate load — what are your options, and which would you actually pick?**
> Options: (1) `.option("mergeSchema", "true")` to explicitly evolve schema for that write, (2) set the auto-merge session/table config for a trusted, well-understood upstream, (3) explicitly `ALTER TABLE ... ADD COLUMNS` first if you want to control exactly what's added, or (4) reject and quarantine the batch if the schema drift indicates an upstream contract break. In practice, I'd default to **not** blanket-enabling autoMerge in production bronze/silver pipelines — I'd add the column explicitly or route unexpected-schema records to a quarantine table for review, because silent schema drift is often a signal of an upstream bug, not a legitimate new field.
