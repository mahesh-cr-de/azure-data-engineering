# Interview Q&A — Clusters, Compute & Databricks Runtime

**Q1. What's the difference between the driver and the executors, and why does driver sizing matter?**
> The driver runs the Spark driver process — it plans the DAG, schedules tasks onto executors, and collects results back for actions like `.collect()` or `.toPandas()`. Executors, running on worker nodes, actually execute the distributed tasks and hold shuffle/cached data. Driver sizing matters because any operation that pulls significant data back to the driver — a broad `.collect()`, a huge broadcast join, converting a large Spark DataFrame to pandas — can OOM the driver even if every worker is healthy and lightly loaded; this is one of the most common "my job just died with no obvious data-skew cause" production bugs.

**Q2. Explain what Databricks Runtime (DBR) is and why you'd pin production jobs to a specific LTS version.**
> DBR is Databricks' curated distribution of Apache Spark bundled with Delta Lake, Photon, common connectors, and (for the ML variant) pre-installed ML libraries, all regression-tested together as a unit rather than assembled ad hoc. You pin production to a specific LTS (Long-Term Support) version rather than "latest" because runtime upgrades can silently change default behaviors — shuffle partition defaults, AQE heuristics, library versions — and an uncontrolled runtime bump on a production job is a classic way to introduce a regression nobody explicitly asked for; upgrades should be tested in a lower environment first.

**Q3. When would you choose a fixed-size cluster over an autoscaling cluster?**
> Fixed-size makes sense when the workload has a predictable, steady resource profile — e.g., a nightly batch job that processes roughly the same data volume every night — because it avoids autoscaling overhead and gives fully predictable cost and runtime. Autoscaling is better for bursty or unpredictable workloads (interactive clusters shared by a team, ad hoc analysis) where load varies significantly and you don't want to permanently provision for peak.

**Q4. Why is scale-down under autoscaling more conservative than scale-up?**
> Because removing a worker mid-job risks discarding shuffle files that worker was holding, which forces Spark to recompute that data on the remaining workers — so Databricks waits to confirm a worker is genuinely idle (not just momentarily between tasks) before decommissioning it. This is also why autoscaling helps more for workloads with natural stage boundaries (many independent tasks/stages) than for a single enormous, tightly-coupled shuffle-heavy stage.

**Q5. What's a cluster policy and why would a platform team use one instead of just training users?**
> A cluster policy is an admin-defined JSON template that restricts what configuration options are available when someone creates a cluster — capping max node count, restricting allowed VM SKUs, forcing an auto-termination timeout, and requiring cost-allocation tags. It's used instead of relying on training because it's enforced structurally: a user literally cannot create an ungoverned, un-auto-terminating, oversized cluster, versus hoping every engineer remembers the org's best practices every single time.

**Q6. What are cluster pools and what problem do they solve?**
> Pools are a set of pre-provisioned, idle Azure VM instances that Databricks keeps warm so that when a cluster is created (or autoscales up), it can attach to already-running instances instead of waiting for fresh VMs to provision from Azure — cutting startup time from minutes to seconds. The tradeoff is you pay for the idle pool capacity even when nothing's attached to it, so pools are worth it for workloads sensitive to startup latency (frequent short jobs, interactive dev clusters) and less worth it for infrequent long-running batch jobs where a few minutes of startup is a rounding error.

**Q7. What does Adaptive Query Execution (AQE) actually change at runtime, and give a concrete example?**
> AQE re-optimizes the physical query plan mid-execution using actual runtime statistics instead of relying purely on static estimates made before execution starts. Concrete example: a join is planned as a sort-merge join because the optimizer's static estimate says both sides are large, but at runtime one side turns out to be small after filtering — AQE can dynamically convert it to a broadcast join. AQE also auto-coalesces shuffle partitions (reducing the "too many tiny post-shuffle partitions" problem from a blanket `spark.sql.shuffle.partitions=200` setting) and can split oversized partitions to handle join skew.

**Q8. How would you choose between memory-optimized, compute-optimized, and general-purpose VM families for a cluster?**
> It depends on where the workload's bottleneck actually is: memory-optimized (e.g., E-series) for wide joins, large shuffles, or heavy caching where you're memory-bound; compute-optimized (F-series) for CPU-bound transformation-heavy workloads with lower memory pressure; general purpose (D-series) as the safe default for mixed ETL where the profile isn't extreme in either direction. In practice I'd start with general-purpose, profile the job (check for spill-to-disk in the Spark UI as a memory-pressure signal, or high CPU utilization with low memory as a compute-bound signal), and re-size based on actual observed behavior rather than guessing upfront.
