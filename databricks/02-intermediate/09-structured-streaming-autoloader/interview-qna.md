# Interview Q&A — Structured Streaming & Auto Loader

**Q1. How does Structured Streaming achieve exactly-once processing, given that failures and restarts are inevitable in a long-running job?**
> It relies on checkpointing combined with an idempotent sink. The checkpoint durably records which offsets from the source have been processed and, for stateful operations, the operator state itself. On restart after a failure, Spark reads the checkpoint and resumes from exactly that point rather than reprocessing everything or guessing where it left off. The "exactly-once" guarantee end-to-end depends on the sink also being transactional/idempotent about re-application — Delta's transaction log is what makes this hold in practice on Databricks, since a reprocessed micro-batch that was actually already committed won't be double-applied.

**Q2. What's the practical difference between Auto Loader's directory listing mode and file notification mode, and when would you choose each?**
> Directory listing periodically lists the source path to find new files — simple to set up with no extra cloud infrastructure, but the listing cost scales with the total number of files already in the path, which becomes a real bottleneck once a landing zone accumulates millions of files. File notification mode instead subscribes to cloud-native events (e.g., ADLS Gen2 via Event Grid) so new file arrivals are pushed rather than discovered by repeated listing, which scales far better for high-volume landing zones at the cost of needing that event infrastructure provisioned — which Auto Loader can largely automate given the right permissions. I'd default to listing mode for smaller or moderate-volume sources and move to notification mode once file counts or listing latency become a measurable problem.

**Q3. Explain what a watermark does in a streaming aggregation, and what happens if you set it too aggressively.**
> A watermark tells Spark how long to keep waiting for late-arriving data for a given event-time window before finalizing that window's result and discarding its state — without one, stateful aggregations would need to retain state forever since data could theoretically still arrive for any past window. If the watermark threshold is set too short, event data that arrives legitimately late (e.g., a mobile client that was offline) but within a reasonable business window gets dropped from the aggregation entirely because its window has already been finalized and its state discarded — silently producing undercounted results with no error raised. The threshold needs to be chosen based on the actual expected lateness of the data source, not an arbitrary default.

**Q4. What's the difference between output modes Append, Update, and Complete, and why can't Complete mode be used for every aggregation?**
> Append only emits new rows since the last trigger and doesn't support unwatermarked aggregations (since a row, once emitted, can't later be "corrected"). Update emits only the rows whose value changed since the last trigger, letting a sink apply incremental changes. Complete rewrites the entire current result table to the sink on every trigger, which requires the full result set to be small enough to materialize and rewrite repeatedly — that's fine for a small dashboard-style rollup (like counts per region) but completely impractical for a large, high-cardinality aggregation, where you'd want Update mode instead so only the delta is written each time.

**Q5. A team wants "streaming-like" incremental ingestion but doesn't want to pay for an always-on cluster. How would you design that?**
> I'd use Structured Streaming's semantics (checkpointed, exactly-once, incremental) but run it with `trigger(availableNow=True)` inside a scheduled job (via Databricks Workflows) instead of leaving the stream running continuously. This processes all currently available new data as a series of micro-batches and then stops the query, so the cluster can be a job cluster that spins up, runs to completion, and terminates — giving the reliability and exactly-once guarantees of Structured Streaming's checkpoint model without the cost of a permanently running interactive cluster. This is the standard Databricks pattern for hourly/daily incremental ingestion that doesn't need sub-minute latency.

**Q6. Auto Loader's schema inference flags a new column in incoming files. What are the options, and what would you actually configure for a production pipeline?**
> Auto Loader supports a few schema evolution modes: `addNewColumns` automatically adds the new column to the target schema and continues, `failOnNewColumns` stops the stream and requires a human/deliberate schema update before it resumes, `rescue` (via the rescued data column) captures unexpected fields into a side column without failing or silently expanding the schema, and `none` ignores new columns entirely. For a production pipeline where schema changes should be a deliberate, reviewed event rather than something that silently reshapes a downstream table, I'd lean toward `failOnNewColumns` (or `rescue`, if the team specifically wants visibility into unexpected fields without an outage) rather than `addNewColumns`, which can let an upstream mistake propagate a bad or unintended column straight into production without anyone noticing.
