# Interview Q&A — Databricks Workflows & Job Orchestration

**Q1. When would you use Databricks Workflows versus Azure Data Factory to orchestrate a pipeline, given that both can technically schedule and chain tasks?**
> They're not fully interchangeable in practice. ADF is the natural choice when orchestration spans multiple Azure services and systems — copying from an on-prem SQL Server, loading into ADLS, triggering a Databricks job, then calling a REST API — because it's designed as a cross-system control plane with native connectors for all of that. Databricks Workflows is the better fit when the entire pipeline is Databricks-native work (multiple notebooks/SQL/dlt tasks with dependencies), since it integrates tightly with cluster management, Unity Catalog lineage, and Databricks-native monitoring without needing a separate service. A common real architecture uses both: ADF as the enterprise-level orchestrator that triggers a Databricks Workflow as one step, and the Workflow internally manages the multi-task Spark DAG.

**Q2. What's the practical cost/isolation trade-off between a job cluster and an all-purpose cluster for a scheduled pipeline?**
> A job cluster spins up fresh when a job run starts and terminates when it finishes, billed at the lower Jobs Compute rate, and guarantees a clean environment with no state or library conflicts carried over from a previous run or another user. An all-purpose cluster stays running (or is manually started/stopped) and is billed at the higher interactive rate; using it for a scheduled production job means paying more and accepting the risk that a notebook someone else is running interactively on the same cluster could affect your job's environment or resource availability. For production scheduled Workflows, a job cluster is the standard choice; all-purpose clusters are for interactive development, or for jobs that specifically need the near-instant start of an already-running cluster and where cost isn't the primary concern.

**Q3. How do you avoid duplicating a job definition for every source table or business unit you need to run the same logic for?**
> Parameterize the job — pass in the source table name, business unit, or environment as a job/task parameter (a notebook widget value or script argument) rather than hardcoding it, so the same underlying job definition can be triggered multiple times with different parameter sets. This is the same metadata-driven principle as ADF's parameterized pipelines (Topic 08) applied to Databricks Workflows. Taken further, Databricks Asset Bundles let you define the job itself as version-controlled, templated code with per-environment parameter overrides, so even the job configuration isn't duplicated across dev/staging/prod.

**Q4. A multi-task job has two Gold-layer tasks that both depend on the same Silver task but not on each other. How does Workflows handle that, and why does it matter?**
> Workflows builds a DAG from declared task dependencies, so once the Silver task succeeds, both Gold tasks — since neither depends on the other — start running in parallel rather than being forced into a single linear sequence. This matters for total pipeline runtime: a naive linear chain would run all three tasks sequentially even though two of them have no reason to wait on each other, needlessly extending the pipeline's critical path. Getting the dependency declarations right (only declaring real dependencies, not just "the order I happened to think of them in") is what unlocks this parallelism automatically.

**Q5. What's a "Run if" condition on a task, and give a concrete case where you'd need one other than "run if all upstream succeeded"?**
> "Run if" conditions control whether a task executes based on the outcome of its dependencies — options typically include all succeeded, at least one succeeded, all done (regardless of success/failure), or at least one failed. A concrete case: a notification/cleanup task that should send an alert or tear down temporary resources regardless of whether the main pipeline succeeded or failed — you'd configure it to run on "all done" rather than "all succeeded," so a pipeline failure doesn't also silently suppress the failure notification, which is a common ADF mistake too when dependency conditions default to Success-only.

**Q6. How would you design retry behavior for a task that calls an external API partway through a pipeline?**
> I'd configure the task's built-in retry policy (max retries with a backoff interval) to absorb genuinely transient failures — a timeout or a 5xx from the external API — without needing custom retry loops inside the notebook code itself, since Workflows already tracks and surfaces retry attempts in the run history for observability. I'd deliberately cap the retry count and use exponential backoff rather than aggressive immediate retries, especially against an external dependency, to avoid hammering a service that might be having a genuine outage. For failures that aren't transient (a 4xx indicating a real data or auth problem), I'd want the task to fail fast rather than retry blindly, which usually means having the task code itself distinguish retryable from non-retryable errors rather than relying purely on Workflows' generic retry-on-any-failure behavior.
