# Interview Q&A — PySpark Transformations, Joins & Partitioning Strategy

**Q1. You have a 500GB fact table joining a 200MB dimension table and the join is slow. Where do you look first?**
> First I'd call `df.explain()` to see which physical join Spark actually chose. If it picked a Sort-Merge Join instead of a Broadcast Hash Join, the likely cause is that 200MB exceeds `spark.sql.autoBroadcastJoinThreshold` (10MB default) — I'd either raise that threshold if 200MB is comfortably within executor memory, or wrap the dimension table explicitly with `broadcast(df_dim)`. If the plan already shows a broadcast join and it's still slow, the bottleneck is elsewhere — likely the scan of the 500GB side itself (file format, predicate pushdown, or partition pruning not kicking in).

**Q2. What's the actual difference between `repartition()` and `coalesce()`, and when would using the wrong one hurt you?**
> `repartition(n)` does a full shuffle to produce exactly `n` evenly-sized partitions; `coalesce(n)` merges existing partitions locally without a full shuffle but can only reduce partition count, and the result can be unevenly sized since it doesn't rebalance data. Using `coalesce()` when you actually need even redistribution (e.g., to fix skew before a wide operation) won't help, because it doesn't move data across the cluster to rebalance — it just merges neighboring partitions. Conversely, using `repartition()` when `coalesce()` would do (e.g., just reducing output file count after a filter) pays for a full shuffle you didn't need.

**Q3. How do you decide what column to partition a Delta table by on disk?**
> I'd pick a column with low-to-medium cardinality that matches the most common filter predicate in downstream queries — date-based columns are the classic choice because most analytical queries filter by a date range and it enables partition pruning to skip irrelevant files entirely. I'd avoid high-cardinality columns like `customer_id` or `order_id`, because that creates a huge number of small partition directories — the "small file problem" — which hurts read performance through file-listing and file-open overhead, often outweighing any pruning benefit. As a sanity check, I'd aim for files in the 128MB–1GB range within each partition, using `OPTIMIZE` (Topic 08) if the natural write pattern produces smaller files.

**Q4. Two datasets need to be joined on a key that's heavily skewed — one value accounts for 40% of rows. What are your options?**
> First option is to check whether AQE's skew join handling is enabled (default on modern DBR) — it detects oversized shuffle partitions at runtime and automatically splits them, handling many skew cases with no code change. If that's insufficient or disabled, I'd manually salt the skewed key: add a random suffix (say 0–9) to the hot key on both sides of the join, which spreads that one key's rows across 10 synthetic sub-keys and thus 10 tasks instead of one, then union/aggregate the partial results. I'd only reach for manual salting after confirming AQE isn't already handling it, since it adds real code complexity.

**Q5. Someone calls `coalesce(1)` before writing a 100GB DataFrame to reduce it to a single file. What's the concern?**
> `coalesce(1)` forces all 100GB through a single task on a single executor for the write — you lose all write parallelism, and that one executor needs enough memory/disk to handle the entire dataset, which risks spill or OOM on a large enough dataset. It's a reasonable choice for genuinely small outputs where downstream consumers need exactly one file, but for large data the better pattern is to write with a sensible number of partitions (sized so each output file lands in the 128MB–1GB range) and, if a single logical file is truly required downstream, merge afterward outside Spark rather than forcing single-task execution inside the job.

**Q6. What's the difference between in-memory partitioning and on-disk partitioning, and why do interviewers ask candidates to distinguish them?**
> In-memory (shuffle) partitioning is about task parallelism during execution — how many concurrent tasks Spark runs for a stage, controlled by `spark.sql.shuffle.partitions` and `repartition()`/`coalesce()`. On-disk partitioning is a physical storage layout (`partitionBy("year","month")`) that groups files into directories so queries can skip irrelevant ones via partition pruning. They're related — writing a DataFrame with 200 in-memory partitions to a table partitioned by year, for a single year's worth of data, produces 200 files inside that one year's directory — but conflating them leads to wrong diagnoses: a "too many small files" problem is a disk-partitioning/write-sizing issue, not something you fix by changing `spark.sql.shuffle.partitions`.
