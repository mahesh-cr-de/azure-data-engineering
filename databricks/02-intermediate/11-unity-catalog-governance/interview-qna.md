# Interview Q&A — Unity Catalog & Data Governance

**Q1. What problem does Unity Catalog actually solve that a per-workspace Hive metastore didn't?**
> A per-workspace metastore means access control, table definitions, and lineage are all siloed per workspace — an organization with separate dev/staging/prod workspaces (or per-team workspaces) has no single, consistent place to answer "who can access this data" or "where did this dashboard's numbers come from" across the whole estate, and permissions could even behave inconsistently depending on which cluster a query ran on. Unity Catalog centralizes this at the metastore level (typically one per region, shared across workspaces): GRANT-based access control, row/column security, and automatic lineage are all enforced consistently regardless of which workspace, cluster, or SQL warehouse a query comes from.

**Q2. Walk me through the three-level namespace and why the catalog level was added on top of the traditional schema.table structure.**
> It's `catalog.schema.table` — schema (equivalent to the old "database") groups related tables, and the new catalog level sits above that as a natural boundary for environment or organizational separation. Before this existed, separating dev/staging/prod, or data belonging to different business units, meant either separate metastores entirely (losing any shared governance) or naming conventions layered onto a flat schema namespace (e.g., `dev_sales`, `prod_sales`), which is a workaround, not a real boundary — it doesn't give you catalog-level permissions, catalog-level storage location isolation, or a clean way to grant "read everything in the dev catalog" as a single statement. The catalog level makes that boundary a first-class, governable object.

**Q3. How would you implement a requirement that regional sales reps can only see rows for their own region, without maintaining separate tables per region?**
> Unity Catalog row filters — define a SQL function that, given the querying user's identity (via `current_user()` or group membership), returns whether a row should be visible, and attach it to the table as a row filter. Every query against that table, regardless of which tool or cluster it comes from, automatically has the filter applied, so a rep querying via a BI tool sees exactly the same restricted view as one querying via a notebook. This is preferable to maintaining separate per-region tables or views because the underlying data stays as one physical table — there's one place to maintain the logic, and no risk of the separate region-specific copies drifting out of sync.

**Q4. What's the difference between a column mask and just not granting SELECT on a sensitive column?**
> Not granting SELECT on a column is an all-or-nothing decision — a user either can query that column or the query fails/the column is entirely absent, which doesn't work when different groups need different levels of visibility into the *same* column (e.g., customer support sees a masked, partially-redacted SSN for identity verification, while a compliance team sees the real value). A column mask instead applies a function to the column's value based on the querying user's group, so the column is visible to everyone but its actual returned value differs by who's asking — same underlying data, differentiated visibility, all governed centrally rather than requiring separate masked views maintained per audience.

**Q5. A schema change is planned on an upstream Silver table. How does Unity Catalog help you assess the risk before making the change?**
> Unity Catalog automatically tracks column-level lineage for everything that reads from that table, so before making the change I'd check the lineage graph (via Catalog Explorer or the underlying system tables) to see every downstream table, view, and dashboard that's derived from the specific column being changed — not just "something downstream might break" but a concrete, queryable list of what actually depends on it. This turns a "hope nothing downstream breaks" change into a "here's exactly what needs to be validated or updated first" change, and the same lineage data can be wired into a CI check that flags or blocks schema changes with tracked downstream dependents.

**Q6. Why does Unity Catalog's approach to storage credentials (External Locations / Storage Credentials) matter for security, compared to the older mount-point pattern?**
> The older pattern typically involved mounting cloud storage into DBFS using credentials configured per-cluster or embedded in notebook code/secrets, which meant storage access was somewhat decentralized and harder to audit — any notebook running on a cluster with that mount had effectively the same access, regardless of the actual user running it. Unity Catalog centralizes this: an External Location plus a Storage Credential (typically a managed identity) is defined once, and access to that location is then governed the same GRANT-based way as tables, tied to the actual querying user/group rather than the cluster's configuration — so audit logs reflect who actually accessed what, and revoking access is a GRANT-level change rather than a credential-rotation or remount operation.
