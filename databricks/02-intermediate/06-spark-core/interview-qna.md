# Interview Q&A — Apache Spark Core

**Q1. Why do DataFrames outperform equivalent RDD code, when they're running on the same cluster?**
> RDDs are just opaque, distributed collections of objects — Spark has no visibility into what's inside them, so it executes your transformations essentially as written, with no ability to reorder or optimize based on data structure. DataFrames carry a schema, which lets the Catalyst optimizer analyze your entire chain of operations, apply rule-based rewrites like predicate pushdown and projection pruning, choose a cost-based physical execution plan (e.g., join strategy), and generate optimized bytecode via whole-stage code generation. The performance gap isn't about DataFrames being "faster syntax" — it's that schema awareness unlocks an optimization layer RDDs are structurally unable to benefit from.

**Q2. Walk through what happens between writing `df.filter(...).groupBy(...).count()` and it actually executing.**
> Nothing executes immediately — Spark builds an unresolved logical plan representing the chain of transformations (this is lazy evaluation). When an action eventually triggers execution, Catalyst runs it through analysis (resolving column/table references, type-checking), logical optimization (rule-based rewrites like predicate pushdown and constant folding), physical planning (generating candidate physical plans and picking the cheapest via cost estimation — e.g., choosing a broadcast join over a sort-merge join if one side is small), and finally code generation, where Tungsten's whole-stage code generation produces optimized bytecode for the chosen plan.

**Q3. What's the practical difference between a narrow and a wide transformation, and why do interviewers care about this distinction?**
> A narrow transformation (filter, map, select) computes each output partition from exactly one input partition, so it requires no data movement across the network. A wide transformation (groupBy, join, distinct, repartition) requires data from multiple input partitions to be combined, which triggers a shuffle — physically moving data across the network between executors, with associated serialization, disk I/O for spill, and network cost. Interviewers care because shuffles are consistently the most expensive category of operation in Spark, and recognizing which of your operations trigger one (and how to minimize or restructure around them) is foundational to almost every real performance-tuning conversation.

**Q4. Why is calling `.count()` in the middle of a pipeline "just to check progress" often a performance anti-pattern?**
> Because Spark's laziness means an action forces full execution of everything accumulated in the plan up to that point — inserting a `.count()` mid-pipeline doesn't give you a free progress check, it triggers a complete, separate execution of the entire upstream chain, and then the pipeline's real final action re-executes much of that same work again (unless something was cached in between). For genuine progress visibility, better options are the Spark UI's live job/stage view, or deliberately caching an intermediate DataFrame if you actually need to reuse it, rather than sprinkling `.count()` calls that silently multiply total work done.

**Q5. What does Tungsten actually add on top of Catalyst — aren't they solving the same problem?**
> Catalyst optimizes the query *plan* — what operations to do and in what order/strategy. Tungsten optimizes the *execution* of that plan at the memory/CPU level: it represents data in a compact binary format (much of it off-heap), avoiding the overhead of one JVM object per row and the associated garbage collection pressure, and it generates specialized bytecode per physical plan rather than relying on generic interpreted operators. They're complementary layers — Catalyst decides "do a broadcast join here," Tungsten is what makes the broadcast join itself run efficiently in memory once that decision is made.

**Q6. How does the number of partitions in a DataFrame relate to cluster parallelism, and what happens if there are too few or too many?**
> The partition count is the unit of parallelism for a given stage — each partition is processed by one task, and tasks are what get scheduled onto executor cores. Too few partitions relative to available cores means some executors sit idle with no work to pick up, under-utilizing the cluster you're paying for. Too many partitions creates excessive per-task scheduling overhead relative to the actual work each task does, which can dominate runtime for small workloads. This is the same underlying idea behind tuning `spark.sql.shuffle.partitions` after a wide transformation, and it's conceptually related to (but distinct from) the small-file problem on disk — one is about in-memory task parallelism, the other about physical file layout, and it's worth being precise about which one you're addressing in an answer.
